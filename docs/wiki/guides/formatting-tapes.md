# Formatting tapes — the dry-run and safety-token flow

Formatting is the only routine operation in OpenBlade that destroys data
irrecoverably. It is therefore two-phase: a **dry run** that changes nothing and
issues a token, and a **confirm** that does the work and consumes the token.

This page explains the flow, *why* it refuses without a token, and one endpoint
that bypasses the whole thing.

---

## The flow

```bash
openblade format dry-run --barcode MCK00001
```

```json
{
  "operation": "format",
  "target": "MCK00001",
  "affected_barcodes": ["MCK00001"],
  "warnings": ["Destructive operation", "Inventory barcode must match confirmation"],
  "is_destructive": true,
  "token": "pQwmEs2ZlP05V4eYhX1JcgJK9gSoTGmpyso0t7ji7YI"
}
```

```bash
openblade format confirm --barcode MCK00001 --token pQwmEs2ZlP05V4eYhX1JcgJK9gSoTGmpyso0t7ji7YI
```

```json
{"success": true, "message": "formatted", "details": {"barcode": "MCK00001", "formatted": true}}
```

Over HTTP the same two steps are:

```
POST /cartridges/{barcode}/format/dry-run
POST /cartridges/format/confirm          # also requires X-Openblade-Service-Token
```

Both CLI transcripts above were run against the simulator.

## What the token actually is

| Property | Value |
|---|---|
| Generated by | `secrets.token_urlsafe(32)` — 43 URL-safe characters |
| Bound to | the operation (`"format"`) **and** the specific target barcode |
| TTL | **300 seconds** (5 minutes) |
| Reusable | **no** — deleted on a successful confirm |
| Stored in | the `safety_tokens` table in the catalog database |

Verified: running the same `confirm` twice fails the second time with
`Unknown or missing safety token`.

If the format itself raises, the token is *not* deleted — you can retry with the
same token inside the TTL. That is intentional: a failed format has not consumed
the operator's intent.

---

## Why it refuses without a token

This is the part worth understanding, because "it refuses" is enforced in two
independent places and only one of them is the token.

**Layer 1 — the token lookup.** `FormatService.confirm()` is the only route from
the CLI and the `/cartridges` API into a format. Before anything else it does:

- token not found in the database → `FormatRequiresConfirmationError("Unknown or missing safety token")`
- token found but its `operation` is not `"format"`, or its `target_barcode` is
  not the barcode you passed → `FormatRequiresConfirmationError("Safety token does not authorize this barcode")`
- token expired → `SafetyViolationError("Safety token has expired")`, checked one
  level down in the domain object

A token is only ever minted by a dry run, and a dry run refuses a barcode that
is not in live inventory. So a valid token is proof that *a human looked at a
plan naming this specific cartridge, in this library, less than five minutes
ago*. That is the property being protected — not secrecy. The token is printed
in plain text; it is a freshness-and-intent receipt, not a credential.

**Layer 2 — the orchestrator.** Independently of tokens,
`TapeOperationOrchestrator` refuses any `FORMAT` request whose
`extras["confirmed_format"]` is not literally `True`:

```
OperationNotConfirmedError: Format operations require explicit confirmation
```

So a caller that reaches the orchestrator directly still cannot format by
accident.

The net effect of the two layers is that "format" can never be the consequence
of one mistyped command. You have to name the barcode twice, in two separate
invocations, within five minutes.

## ⚠️ One endpoint bypasses all of it

`POST /ltfs/format` formats a tape given only:

```json
{"barcode": "VOL001L9", "confirm": true}
```

No dry run. No token. No `X-Openblade-Service-Token` header. No authentication.
It satisfies layer 2 by setting `confirmed_format` itself, and it never reaches
layer 1 because it calls the orchestrator directly — where `_format()` **mints a
fresh `SafetyToken` for itself** when the caller did not supply one.

This was confirmed empirically against the simulator: the call returns
`{"status": "completed"}` and the tape is formatted.

Operator guidance:

- Treat `/ltfs/format` as a destructive, unauthenticated endpoint. Do not expose
  the OpenBlade API to any network you do not control, and if you front it with a
  proxy, block `POST /ltfs/format`.
- Use `openblade format dry-run` / `confirm`, or the `/cartridges` pair, for
  anything an operator drives.
- `docs/safety.md` states that formatting requires a dry run and a valid token.
  That is true of the documented path and **not** true of `/ltfs/format`.

Omitting `confirm` does refuse — but it currently surfaces as an unhandled
`OperationNotConfirmedError` rather than a clean 400.

## Error handling is ugly, not absent

The CLI prints a full Rich traceback for a safety refusal:

```
FormatRequiresConfirmationError: Unknown or missing safety token
```

…preceded by twenty lines of stack. The message on the last line is the real
one. Only `openblade hardware connect-i3` has a curated error handler; the rest
of the CLI lets exceptions escape. Cosmetic, but do not mistake the traceback
for a crash — the refusal worked.

Over HTTP the same errors are clean: both `FormatRequiresConfirmationError` and
`BarcodeMismatchError` map to **400** with
`{"error": "<ClassName>", "detail": "<message>"}`.

## Before formatting a real tape

- Work through `docs/runbooks/safe-format-checklist.md`.
- Confirm the barcode against physical inventory, not against a list you typed.
- On real hardware, formatting targets a device node resolved from the drive the
  cartridge is loaded in. If your drive correlation is wrong, you format the
  wrong cartridge. Set `OPENBLADE_DRIVE_SERIAL_MAP` first —
  [drives & changer ops](drives-and-changer.md).
- The hardware test suite only formats barcodes listed in
  `OPENBLADE_SCRATCH_BARCODES`. Keep real data out of that variable.
